# V1 异步研究

`v1_async` 在 [V1 Explorer](v1.md) 上增加持续异步调度，来源和 Explorer 同步范围见该文档。
这是 AlphaAtlas 的本地并发适配，不是 ChaoticTrader_Future 完整 pipeline 的复现。
旧 `v1` 和 `annealing` 的搜索机制、配置及恢复入口继续保留。

状态字段沿用[研究计划命名](annealing.md)：每组使用 `research_plan_state`，
`next_research_plan_index` 分配新的计划编号，`completed_research_plan_count` 记录完成数量。
两者不因异步完成而相互替代。历史组内的 `round`、`next_index` 在加载时读取，原文件不改写。

## 调度与职责

```text
Explorer：最新地图 → 二至四个提案 → 按评分选择空闲组所需的方向
                              ├─ Analyst A → Miner A ↔ 平台反馈
                              ├─ Analyst B → Miner B ↔ 平台反馈
                              └─ Analyst C → Miner C ↔ 平台反馈
某组完成 → 退火裁决 → 下一次 ask 用最新地图启动 Explorer 补位
其他组继续执行，不等待整批完成
```

- `parallel_plans` 控制并行研究组数，默认 3；每组内保持 Analyst → Miner 的顺序。
  各 Miner 只接收本组计划和本组逐次评估，反馈后才能生成本组下一候选。
- 最多一个 Explorer 请求链。每次提交二至四个完整且实质不同的提案，按原 30/30/20/20 评分排序，
  取空位和预算允许的前若干项；未选提案不排队。Explorer 可与其他组同时调用模型。
  提示词附一句说明 `available_slots` 是当前可启动的计划数，服务端最多启动这么多个方向，其余丢弃。
  每批二至四个提案与实际空位数分别处理：按 `parallel_plans`、剩余预算和最多四个空位
  创建研究组。即使只剩一个空位，也从合格批次中择优执行一个，其余提案不排队。
  输入列出正在研究的提案，服务端拒绝机制、条件、预测和竞争解释均重复的方向；
  同一 Region 允许研究不同方向。这是结构重复检查，不声称能识别所有语义改写。
  已完成方向允许按 [V1 回访规则](v1.md#一轮研究)继续研究；历史方向不作为永久排除列表，
  与活动计划的重复检查、四项评分及原有候选准入保持不变。
- 新 Explorer 在 runner 更新地图之后启动，其输入保存为该次探索的快照。
  历史索引及整组计划证据继承 [V1 历史读取](v1.md#按计划读取历史)：按 `research_plan_index`
  关联交错的 trial，草稿中的未展开历史引用先补全并确认，再按空位创建研究组。
  每个 Analyst 通过原 `sources` 收到被引 trial 的同计划结果；补全和确认也由协调线程保存。
  Explorer 自动展开的已完成计划限于最近 `parallel_plans` 组，旧计划按引用补全；恢复时
  已保存的过大输入也按同一规则收敛，已校验引用与对话证据保留，见 [V1 恢复](v1.md#配置失败与恢复)。
  进行中的研究保留自己的方向和计划。新 Analyst 的历史反馈来自最近完成的计划，
  沿用原有效覆盖、已入库和主验证指标 Top-K 筛选，并保存该反馈快照。
- 后台线程只发不可变消息副本对应的一次 HTTP 请求，不访问 SearchSession、地图或检查点。
  主线程接收回复，复用 V1 的查询、评分、修复、字段校验和 Miner 对话流程。
  已完成组先推进；同一次调度看到多个可提交候选时，按研究组创建顺序提交。
- runner 仍逐个 `evaluate → tell → atlas.observe`。评估、去重、入库和原子 trial 都是单写入者，
  模型 I/O 可以在评估期间继续。没有引入第二套工具、任务队列或结果账本。
- `parallel_evaluations`（默认 1，不超过 `parallel_plans`）允许不同研究组的候选同时计算，做法同
  ChaoticTrader_Future Miner 的 `max_parallel`：线程池只做 Train／Valid 计算（`SearchSession.measure`），
  准入、残差、原子 trial、`tell` 和地图更新仍由主线程按 trial 编号逐个执行，评估器只在共享缓存
  读写处加锁。每组至多一个候选在算，Miner 仍须先收到本组反馈。候选交出时即写入检查点的在算列表
  （`pending` 为列表）；恢复时已提交的 trial 直接取用，未提交的重新计算。为 1 时走原串行路径，
  配置中不记录该字段。生成候选时看到的地图可能落后于尚未准入的在算候选，因此与串行运行不是
  同一轨迹，比较时需固定并披露此值。
- `parallel_explorers`（默认 1，不超过 `parallel_plans`）允许多条 Explorer 对话同时为空闲计划位
  提出方向，每条仍最多开四个计划。新对话启动时扣除已运行对话认领的计划位与尝试额度，不会超开；
  各自在启动时保存输入快照，提交时另与其他对话已开出的计划做重复检查，重复则按原修复流程退回。
  请求以 `explorer`、`explorer-2`… 区分；为 1 时检查点仍保存单个 `explorer`，配置不记录该字段，
  大于 1 时保存 `explorers`。用于 Haiku 等计划提前结束较多、单个 Explorer 补位跟不上的情形
  （V3 Haiku 10 并发运行中仅 3／10 个计划位在用）。

三个角色都能使用五个公共只读查询工具，具体查询协议和上限见 [V1](v1.md)。
Analyst 和 Miner 的查询由协调线程执行并保存，后台模型线程不访问 SearchSession。

## 预算、退火与可比性

配置位于 [v1_async.toml](../../configs/v1_async.toml)。`candidates_per_plan` 默认 5。
调度前从剩余尝试数扣除活动计划尚未使用的额度；新空位按可用额度均分，每组不超过配置上限。
Explorer 进行中的额度也已预留，预算尾部可缩短计划，避免额外生成无法评估的候选。
只有 runner 的实际提交消耗公共预算，非法、重复和拒绝沿用平台规则。

Region 的累计入库率奖励和 Metropolis 公式不变；每个提案批次在启动 Explorer 时固定温度，
计划结束时按实际完成顺序更新共享 Region 得分和当前 Region。结束一个计划即可补位。
模型返回时序会影响候选提交、去重和退火次序，因此同 seed 不保证重现原串行轨迹，
也不保证两次新异步运行得到同一轨迹。比较实验需固定并发数并披露此差异。

## 失败与恢复

对话上限及收敛提醒沿用 [V1](v1.md)：默认最多 40 轮，Explorer 从第 21 次请求开始持续提醒
优先提交方向，仍允许必要查询；第 40 次合格回复正常接受。每次补位探索单独计数，
并使用该 Explorer 已保存的回复数恢复提醒，不影响其他组进度。
旧检查点中已保存的 `unresolved` 也按 V1 的规则在剩余额度内澄清一次；
补位 Explorer 在有活动计划的快照上仍报告不足时，暂停该次补位，让原计划继续完成。
等待期间复用已保存回复，不重复请求 Explorer，也不新增候选或消耗尝试预算；
所有原活动计划完成后，将不足对话保存到最后一条研究记录的 `deferred_explorer`：有实际
trial 时使用 `factor_trial_records`，全部为零提交阻塞时使用原 `blocked_plans` 记录，
再基于最新地图开启新 Explorer。旧检查点中连续两次不足且仍有活动计划的情况可直接恢复，
无需手动清除 Explorer。若旧回复到达时快照中的计划已全部完成，也按新证据重新选题。
新证据包含最近完成计划的全部候选结果，并将引用定义交给 Analyst；范围与交接见
[V1 的一轮研究](v1.md#一轮研究)。失败或未入库的试验不会因不在正式库而被省略。
新的 Explorer 没有活动计划可等待时，depth 不足先在原对话内转为全图 breadth；
保留原始不足报告，恢复也不重复已保存回复或重置对话额度，规则见
[V1 失败与恢复](v1.md#配置失败与恢复)。breadth 仍不能提出可执行方向时，方法返回
`ExplorerUnresolved`，runner 正常保存和冻结已有结果，报告实际提交数及提前结束原因。
这只是模型在当前信息和能力下的研究判断，不是平台验证整个搜索空间已穷尽。

复用原 JSON 方法检查点，保存各组的方向、计划、回复、Miner 对话、额度、待提交候选，
以及 Explorer 状态、全局 RNG、退火状态和唯一待反馈候选所属组。Future 和线程不持久化。
已保存回复不重发，已提交 trial 复用原反馈；请求已发但回复尚未写入检查点时，恢复可能重发，
原请求用量保留 unknown。HTTP 408/429/500/502/503/504、网关 520–524、连接失败等沿用公共客户端的重试分类，
由主线程执行最多 3 次额外重试；一般错误等待 1/2/4 秒，HTTP 429 或响应体明确限流时
等待 30/60/120 秒。有效的 `Retry-After` 秒数或 HTTP 日期作为等待下限，
等待期间其他组可继续推进。持续限流仍明确停止，可在服务恢复后沿原检查点续跑。
HTTP 200 但没有文本的代理响应，以及响应体内明确的服务过载，沿用相同重试和请求计数。
这些重试不生成 trial、不消耗候选预算；输出额度截断、拒绝和意外工具调用仍显式失败。

补位 Explorer 的查询或格式修复耗尽对话时，若其启动快照有活动计划，也进入上述等待：
保留全部回复和错误，让原计划完成，再将对话保存到原 `deferred_explorer` 并用新证据补位。
这包括旧终止检查点中活动计划已完成、但失败 Explorer 尚未归档的情况；恢复不重发旧回复，
不重置本次对话计数，不把格式失败解释为模型宣布研究空间耗尽。没有活动计划可等待的
Explorer 格式或查询对话耗尽、Analyst 耗尽修复或模型硬错误仍显式终止运行。
Analyst／Miner 的结构化 `blocked` 则结束本组，
释放未用额度，其他组继续，Explorer 按最新阻塞原因补位；复用
[计划阻塞与交接](annealing.md#计划阻塞与交接)，不生成空公式失败 trial。
部分已执行计划按自己的编号结束，不把其他组最后完成的 trial 当作本组记录。
Miner 格式/表达式修复耗尽仍提交生成失败
候选并扣一次尝试。退出会取消尚未开始的请求；已经在网络中的请求受 HTTP 超时约束，
可能延后结束，但不会再写入研究状态。异步请求不逐 token 输出，避免并发回复污染终端。

并发配置纳入原冻结校验。旧串行 run 使用原方法续跑；启动异步实验需新建 run。
`generation_seconds` 是 runner 等待下一个候选的墙钟耗时，包含并发重叠，不能视为单请求延迟。
实际请求及已知 token 仍逐次累计；加速幅度取决于模型服务吞吐、限流与评估耗时。

## 运行与验证

```bash
uv run --env-file /home/ziyi/AlphaAtlas/.env atlas run \
  --asset futures_kernel_5m_full --universe all --fold fold1 \
  --method v1_async --seed 42 --attempts 1000
```

该命令与完整字段 AlphaPROBE 使用相同的 Kernel 复权 5m 资产、fold 和 seed；
新运行默认开放当前快照全部可用特征，不需单独添加 `--fields`。
模型、服务和凭据环境变量名由方法配置控制，切换后新建运行；恢复时须匹配原运行的冻结配置。

配置只保存凭据环境变量名；上面的启动命令加载本项目 `.env`，不将凭据写入运行产物。
测试使用合成数据、模拟回复和线程屏障，验证 Analyst 重叠、慢组期间补位、反馈隔离、预算尾部、
单线程写状态、重试计费、阶段中断、未完成请求恢复、原子 trial 恢复和配置冻结；
另覆盖补位不足或对话耗尽时完成活动计划、等待状态恢复、迟到不足回复、最新证据补位及
无活动计划时的 depth→breadth、原始报告保留、切换后的中断恢复和全图不足时正常冻结。
真实服务吞吐与市场表现需要独立实验，不由这些测试推断。
